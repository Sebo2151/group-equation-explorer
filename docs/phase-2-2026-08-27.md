# Phase 2 implementation record, 2026-08-27

Phase 2 of the [development plan](development-plan.md): the core expression
workbench. This record states what was built, the decisions taken where the plan
left a choice open, what was verified, and what is still not done.

The Phase 1 slice and its [audit record](audit-2026-08-27.md) are the baseline.
Every invariant the audit's browser suite established still holds; see
"Verification" below.

## Decisions taken

The plan left several choices open. These were the recommendations put to the
user, and they are what the code does. They are recorded here because a later
reviewer should be able to tell a decision from an accident.

| Question | Decision |
| --- | --- |
| Powers | Kept as notation. `a^3` is a power node; writing it out or combining exponents is a rule that costs a step. |
| Input syntax | Juxtaposition, with `*` and `·` optional. A generator is one letter plus digits, so `r2` is a generator and `a^2` is a power. |
| Rule catalogue | The full catalogue is implemented in the kernel; each challenge names the subset it permits, and that ruleset is recorded with the proof. |
| App shape | Six data-driven challenges plus a free exploration mode with an editable start expression. |
| Insertion | The learner names the term, with a live typeset preview; every gap is then marked as its own control. |
| Export | Structured proof record (JSON) and LaTeX, plus a size-limited share link. No file download. |

## The term model

`app/term.ts`. A term is a generator, the identity, a flat product, an inverse,
or an integer power.

Structural normalization is **only** associative flattening. Building a product
splices nested products, an empty product is the identity, and a one-factor
product is that factor. Nothing else is normalized: identity factors are not
removed, inverse pairs are not cancelled, inverses are not distributed, powers
are not expanded or combined. Those are the steps the app exists to teach.

Two notational decisions are load-bearing:

- **Exponent 1 and -1 never reach a power node.** `power(x, 1)` is `x` and
  `power(x, -1)` is `inverse(x)`. Two spellings of one term would make
  structural equality wrong, and every rule that matches on it wrong with it.
  Exponent 0 *is* kept, because `x^0 = e` is a step worth taking explicitly.
- **`e` is reserved.** No generator may be named `e`, or `e` followed by digits,
  so a rendered `e` always means the identity.

### Targets: paths, spans, and gaps

A target is `{ path, start, end }`. The path addresses a node by descending
child indices; `start..end` is an inclusive span of factors within that node.

Two things make this cover every case with one shape:

- A node that is **not** a product behaves as a one-factor list, so `0..0`
  addresses the node itself. `(ab)^-1` is targeted the same way a factor is.
- An **empty span** — `end === start - 1` — is the gap before factor `start`.
  That is what the insertion rules attach to, and it needs no separate type.

`hosts()` enumerates every node that can host a span: a product hosts its own
factors, and a non-product hosts itself *only when its parent is not a product*.
Without that condition a factor's single-factor span would duplicate a span of
its parent, and one rewrite would get two controls.

This is what lets a rule address the `ab` inside `(ab)^-1 a b` — path `[0, 0]` —
which the plan named as the requirement the flat model could not meet.

## The parser

`app/parse.ts`. The accepted grammar, and nothing else:

```text
expression := factor+
factor     := atom ( '^' exponent )?
atom       := generator | 'e' | '(' expression ')'
generator  := letter digit*
exponent   := '-'? digit+          (braces optional: a^{-1})
```

`a^2^3` is refused rather than guessed at: the message asks for parentheses.
Limits are 240 input characters, exponent magnitude 64, nesting depth 16, and
400 nodes, all enforced during or immediately after the parse. Errors carry a
character position, and `tryParseTerm` returns failure as a value so the input
fields can show it live rather than throwing.

`termSource` is the inverse: `parseTerm(termSource(t))` reproduces `t`, and
re-printing is stable. That round trip is what lets a proof record store terms
as text rather than as a second encoding of the tree.

**Security note.** The audit identified `factor.base` reaching TeX unescaped as
the latent injection point "as soon as a parser or import exists". It now does
exist, and the mitigation is unchanged and is the reason it holds: the accepted
generator alphabet is `[A-Za-z][0-9]*` and is validated, so nothing that could
be a TeX command can reach the renderer. `\href{javascript:…}` and
`\rule{9999em}{9999em}` are parse errors, not rendered content. KaTeX options
stay pinned in one place in `page.tsx`.

## The rule catalogue

`app/rules.ts`. Fourteen rules, each with matching and rewriting defined in one
table entry, so an unknown or half-implemented rule is a lookup failure rather
than a fallthrough into another rule's behaviour — the shape the audit's first
defect motivated, carried forward.

| Family | Rules |
| --- | --- |
| Inverses | cancel inverse pair, insert inverse pair, undo a double inverse, write as a double inverse, distribute an inverse, collect into one inverse |
| Identity | remove identity, insert identity, invert the identity |
| Powers | write a power out, combine powers, zero power, invert a power, split a negative power |

Every one is a theorem of any group. Directions come in pairs where the reverse
is finitely instantiable; `insert-inverse-pair` is the exception the plan
anticipated — it has infinitely many instantiations, so it asks for the term
rather than pretending to enumerate them.

Cancellation matches structurally, not up to provable equality: `x` and `x^{-1}`
cancel, and `x^n` and `x^{-n}` cancel, but `ab` and `b^{-1}a^{-1}` do not. They
are equal, and proving it is the point of the socks-and-shoes challenge.

Rules that could grow a term without bound — expanding a power, wrapping a
double inverse — check the node and depth budget while enumerating targets, so
an impossible move is never offered rather than failing after it is chosen.

### Circularity

A rule being sound is separate from a challenge being allowed to use it. Each
challenge declares its permitted rules; the proof records that ruleset; and
`applyRule` on the proof refuses anything outside it, as does replay. An
imported record that claims a known challenge is rejected if its start, goal, or
ruleset does not match what that challenge declares — so an edited file cannot
present a proof built with extra tools as a solution to a challenge that forbids
them.

`tests/challenges.test.ts` searches for an actual proof of every challenge using
only that challenge's own rules, and replays what it finds. That is the plan's
"author and check an actual proof of each challenge using exactly its permitted
tools before shipping it", executed rather than asserted.

## Proof records and replay

`app/proof.ts` keeps the pure reducer shape from Phase 1 and adds the ruleset,
the goal, and the instantiated term on each step. `replayProof` rebuilds a proof
from its recorded steps alone, through the same contracts, and names the step
that fails. `verifyProof` replays a proof against itself.

`app/serialize.ts` exports that record as JSON, exports the chain as LaTeX, and
encodes a short proof into a URL fragment. Import validates the envelope, the
ruleset, and each step's shape, then replays — a label saying "Inverse law" is
an annotation, and only the replay makes it evidence. Records are limited to
20,000 characters and 200 steps before any parsing begins, and a proof too long
for a link is refused rather than truncated.

## Rendering nested terms

`app/render.ts`. A term is laid out as a row of tokens sharing one CSS grid with
the candidate controls, so a bracket spans exactly the columns of its
sub-expression without measurement JavaScript. Two details matter:

- **Superscripts are their own token**, riding on an empty TeX base. Glued to
  their base, the `a` inside `a^{-1}` and the whole `a^{-1}` — two different
  targets — would cover identical columns and be indistinguishable on screen.
- **Columns alternate**: insertion point, token, insertion point. That gives a
  zero-width insertion control somewhere to live, and the insertion columns are
  given width only while an insertion rule is selected, so the spacing of the
  mathematics is otherwise untouched.

`placeTargets` layers overlapping controls onto separate rows, generalising the
Phase 1 treatment from factor spans to arbitrary column intervals. Two insertion
points that coincide on screen at different depths — before `a^{-1}` and before
the `a` inside it — are correctly two controls on two rows.

## Interface

- A challenge picker; the rule panel shows only the challenge's own laws,
  grouped by family, each with a live candidate count.
- Free exploration with a start expression and optional goal, both with live
  typeset previews and inline parse errors.
- An instantiation field for insertion rules, with an inverse-first toggle. The
  candidate controls are disabled while the term does not parse.
- Share panel: copy the proof record, copy LaTeX, copy a link, paste a record to
  import.
- Keyboard: arrows move between candidates and wrap; digits 1–9 apply a
  candidate directly; Ctrl/Cmd+Z and Ctrl/Cmd+Shift+Z undo and redo.

### One change the new content forced

The mobile dock reservation could no longer be a constant. In Phase 1 the dock
held two laws; it now holds between two and fourteen depending on the challenge,
so `--dock-height` is measured from the dock with a `ResizeObserver` and
published on the document element. The Phase 1 browser test that pins the dock
off the active line caught this — it failed at 712px against a 650px dock — and
a new test repeats the check in free exploration, where the dock is tallest.

## Verification

- `npm test`: 126 Node tests across `term`, `parse`, `rules`, `render`, `proof`,
  `serialize`, and `challenges`, up from 53.
- `npx tsc --noEmit --incremental false`: clean.
- `npm run lint`: clean.
- `npm run test:browser`: 59 tests. The 23 Phase 1 invariants pass **unchanged
  in substance**; two assertions were updated only because span speech now reads
  "a times a inverse" instead of "a, a inverse". 36 new Phase 2 tests cover rule
  gating, nested targets, bracket geometry, insertion gaps and the blocked
  control, powers, free-mode input and its rejection, import/replay/refusal,
  share links, the keyboard, and the dock at its tallest.

Three things about writing the new suite are worth recording, because each one
was a test that looked like it was working and was not:

- **A retry that confirms its own input proves nothing.** The first version of
  the challenge-picker helper selected an option and then asserted the select's
  value — which `selectOption` sets whether or not React is listening. Every
  test that changed challenge passed its setup and then failed downstream, and
  the suite took 8.8 minutes to report it. The helper now waits for the
  challenge number in the banner to change, which only the app can do.
- **The hydration gate must not share a signal with anything under test.** It
  first waited for `--dock-height` to be set, which is the dock fix itself.
  Reverting that fix then failed every Phase 2 test in `beforeEach` with
  "waiting for hydration" rather than failing the dock test on its geometry.
  The gate now toggles the reasons control and watches its label change, and
  puts it back.
- **The suite was mutation-tested.** Reverting the dock measurement must fail
  the dock tests. On the first attempt it did not: the new test's proof was too
  short to push the active line under the dock, so it passed against the broken
  code. It now runs five steps in free exploration, where the dock is tallest,
  and both dock tests fail on the geometry assertion when the measurement is
  removed (485px available against a line ending at 537px). A regression test
  that has never been seen to fail is not yet evidence of anything.
- Manual browser pass at 1280x720: all six challenges, free exploration with
  `(r2 s)^-1 r2^3`, import and refusal, no console errors.

## Deliberately not done

Everything from Phase 3 onward: equations, whole-equation operations,
implication, teaching modes, hints, unlocks, progress storage, personal bests,
custom relations and presentations, and bounded proof search. The
`tests/challenges.test.ts` search is a test fixture, not a hint engine — it is
not exposed, bounded for the user, or cancellable.

`app/core.ts` and `tests/core.test.ts` were removed: the flat `Factor[]` model
they held is superseded by `app/term.ts`, and keeping a second representation
alive would be the surest way to get two meanings of "expression".
